# WorkBuddy 审计报告复核与建议（2026-10-01）

本页是对 [WorkBuddy 原审计报告](code-audit-2026-10-01.md) 的复核意见，不是修复完成记录或现行业务规则。原报告保留原样；附件中的修复路线属于待评估建议，不构成执行指令。用户本轮要求先给全面建议、不修改代码。

核对对象为本地 `codex/manual-position-protection` 工作区，HEAD 为 `654df14d2022d7bb12f12d7efdd3b42df94262bf`，包含既有未提交修复。核对现行文档、报告涉及的源码、调用关系、相关测试及锁定版本的 Django / SimpleJWT 源码；没有重新逐行审计全部仓库，也没有查询生产状态。以下“成立”主要指本地源码支持问题判断，涉及生产可达性或并发结果时另行标明。问题状态统一维护于 [已知事项](known-issues.md)。

## 总体意见

报告找到了多项真实问题，尤其是新开仓币种白名单、条件单恢复、无界回测、趋势提醒丢失及前端演示数据残留。长文件和重复代码也值得治理。但其“11 个 P0”“未发现直接资金风险”“死代码删除零风险”不能直接作为排期和安全结论。

主要需要纠正：

- 把账户选择参数当成权限来源，忽略既有模式绑定与隔离，误判 `X-Trading-Mode`。
- 忽略 `CHECK_REVOKE_TOKEN=True`，误判密码重置后旧会话仍可操作资金账户。
- 忽略 Django `get_or_create` 内建的唯一冲突恢复，将正常竞争直接判为缺陷。
- 将内部容器 HTTP 与公网第三方传输混为一谈，提出会破坏当前通知配置的强制 HTTPS 改法。
- 将信息缺失改成默认值，可能悄悄改变止损触发参考价；将撤单优先级改成绕过交易所冷却，也可能扩大限频事故。
- 把界面显示、资源耗尽、通知可靠性、认证输入和交易保护统一列为 P0，难以识别真正需要优先处理的交易恢复问题。

评分与行数只能帮助定位维护压力，不能证明资金安全。验收应关注：未知结果不会再次交易、保护替换没有空窗、订单归属不会被读请求改变、失败不会伪装成零、后台保护不会被低优先任务挤占。

## 报告遗漏的优先问题

这些问题已在 [第二轮已知问题](known-issues.md#业务规格与产品行为-1) 记录，本轮独立重跑了前两项及认证反例，没有把旧测试记录写成本轮全量通过。

1. **REVIEW2-S1：未知下单结果再次 POST。** [opening.py](../server/trading/opening.py) 在 `recovered_row=None` 时执行 submit，重试路径未持久区分“确证未提交”和“已尝试但结果未知”。真实限价路由的模拟复现：第一次超时，按 ID 查询空；再次操作同请求，POST 次数从 1 增至 2，客户端 ID 相同。查询恢复成功的对照保持 1 次。此结果证明应用再次提交，未实盘证明重复成交。[Binance 只要求客户端订单 ID 在活动订单中唯一](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/trade)，不能据此承诺永久幂等。建议在交易所 POST 前持久提交尝试标识；未知结果只恢复，不因查询空或查询限频自动重发。崩溃发生在标识落库与真正发送之间时也必须维持未知，不能按超时年龄清除。
2. **REVIEW2-B1：前置拒绝仍留下 pending，阻塞手动仓接管。** 限价资本预检失败没有发任何交易所 POST，已创建的请求仍 pending；随后同身份同币种出现浮亏超额的手动仓，扫描接管 / 保护调用均为 0。仅在合成数据中把这个确证未提交的请求设为 failed，对照为 1 / 1。建议统一终结尚未尝试写入的拒绝路径；没有交易所订单号并不能证明未发送，不能放行未知结果请求。修复时要与 S1 使用同一提交事实模型。
3. **REVIEW2-B3：回测结束时间在未来，未收盘数据仍可能入结果。** 与 P0-7 资源上限同批处理。报告“防前视完备”不能从样本采集守卫推导到所有回测路径。
4. **REVIEW2-S2：生命周期成交查询跨过 7 天接口窗口。** 长持仓可能持续无法补齐关闭证据与手续费；只增加重试不改变非法查询范围。与真实 / 估算财务、分页完整性一并安排。
5. **REVIEW2-S3：异常资金历史回包降成空列表并推进游标。** 影响历史完整性，须失败保留游标，不能记录成真实零。另有 REVIEW2-B2 开仓手续费证据口径、S4 完成邮件缓存异常反转 API 成功、B4–B7 前端详情竞态 / 续页重发 / 重采集入口 / K 线标记偏移，原审计路线不能覆盖这些已有问题。

因此不赞同原报告“未发现会直接造成资金损失的逻辑错误”被解释为安全背书，也不赞同“前端竞态防护示范级”被解释为所有异步入口均已隔离。系统有良好基础，仍需对具体失败路径作证明。

另外六项建议：

- **涨跌颜色**：同意收敛主题变量，但用户习惯不能仅按“大陆用户”自动推断。保留当前习惯或后续提供明确选择；这属于产品决定，不是代码错误。
- **旧 Key 转账历史增长**：保留旧身份隔离和可核对历史是有意设计，不能因为换绑就删除。若规模需要，先测数据量、索引、查询成本，再定义保留期、归档及用户访问方式。
- **OKX 兼容命名**：目前是 Binance 适配后的内部 DTO，`instId`、`posSide`、`sz` 等被多个业务模块消费。没有证明仍使用第二家交易所；全仓改名不只是删除死代码。优先局部封装，只在收益明确时作独立契约迁移。
- **同步查询出口 IP**：成立，已有 600 秒成功值缓存，但查询失败得到空值后下一次仍会外呼；限频期间诊断不应增加同步 2.5 秒等待。优先固定配置，失败也短暂缓存或移到诊断任务。配置地址应标注为预期值，不能伪称实际出口已测得。
- **watch_plans 手工校验**：适合换 serializer，但先固定旧行为中默认、清空、非法字段、枚举、金额有限性和日期的契约，避免迁移后默默改写用户资料。
- **科学计数法 / 合计浮点**：小价格展示问题成立，应用已有 chartPrice，可逐步统一显示口径；盈亏合计应明确“原始值相加再舍入”或“已展示逐笔金额相加”的产品口径，避免精确计算与显示舍入差被混为一谈。服务端金额权威与前端显示必须分开。

## 建议实施顺序与验收

1. **交易事实与归属先修。** 未知请求不重复 POST、确证未提交的拒绝正确终结、GET 不认领 / 改写保护归属、条件单终态恢复。每项单独建立失败与正常对照；避免在大重构中调整这些状态转换。
2. **新风险入口与资源约束。** 系统 / 组合币种校验、回测根数 / 页数 / 时间 / 并发、研究预算退让、未来 K 线过滤、认证畸形输入及可信代理边界。未知请求恢复和存量管理不得被新开仓限制挡住。
3. **后台一致性。** 缩短网络外层事务、稳定用户策略互斥、长持仓查询窗口与财务完整性、采样遗漏。锁 / 约束变更做隔离 MySQL / Redis 验证，不凭 SQLite 推断生产。
4. **通知和前端小修。** 趋势失败可补发、内部通知禁重定向、Mock 移除、归集按钮门槛、详情竞态和分页退避。无真实资金动作也可完成有意义验证。
5. **纯移动和减法。** 在行为基线稳定后分别收敛 helper、拆视图 / 页面、清理确认废弃的方法和依赖；最后才评估内部 DTO 改名。每批留可定位的差异，兼容存量数据和回滚代码。

最有价值的验收不是“删了多少行”，而是：

- 模拟 POST 超时、空恢复、恢复查询限频、已成交后查不到、进程在提交前后中断，同一请求不再次写交易所。
- 活动条件单、已触发、已取消、延迟可见、身份冲突各自走正确分支；替换期间原保护保持有效。
- Web / 外部仓、策略 / 手动 TP、不同 Key / 用户 / 模式 / 生命周期互不认领，列表请求不改变后续可撤单集合。
- 高成本研究在准入处被拒绝，保护仍有预算；真正限频遵守退避，不靠撤单绕过封禁。
- 密码重置、恶意 UID、非字符串 email、非 ASCII token 均返回预期响应；旧会话被拒绝，代理身份不可伪造的结论有实际部署证据。
- 金额门槛用 1000.01 / 1000.009 等边界，多币种价格与未知余额保留正确语义；页面换账户、换模式、失败与卸载不会接受旧回包或无间隔重发。
