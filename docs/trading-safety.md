# 交易安全边界

> 本文维护整合版沿用的业务规则；当前运行与验证边界见 [整合说明](INTEGRATION.md)。来源项目历史资料从 [来源索引](sources.md) 查询。

本文定义维护时必须保留的行为，依据 [交易服务](../server/trading/services.py)、[执行适配](../server/trading/execution.py)、[仓位生命周期](../server/positions/lifecycle.py) 和相关测试。未落地的额外加固另列 [已知事项](known-issues.md)，不能当作已有防线。

规则核对日期：2026-09-30；本轮审阅修复的发布状态见 [已知事项](known-issues.md#2026-09-30-全仓代码审阅修复)。

## 授权不是交易指令

部署授权只允许发布或相关运维，不包含开平仓、划转、撤销既定止损 / 止盈、改变已有订单策略或写入人工接管状态。此边界同样适用于数据迁移、Django shell、修复脚本和应用启动逻辑。当前 SSH / webhook 授权以 [运维文档](operations.md) 为准。

保留订单已有保护，不能为消除日志报错撤掉保护单，也不能通过“手动管理”标记关闭自动修复。诊断优先只读；有资金副作用的动作须单独明确授权。

## 开仓与并发

- 每个 API 同时最多两笔风险敞口，真实活动持仓和未成交限价委托都占用额度，不能只数本地订单行。
- Web 手动市价、限价和追单在首仓前做资金预检；这不是全部交易 API 的统一凭证闸门，不应悄悄扩展成另一套后端授权协议。
- 请求使用稳定 ID 和持久化 `TradeOpenRequest`。网络异常、HTTP 5xx 及 Binance `-1000 / -1006 / -1007` 属于“结果未知”，先按同一客户端订单 ID 恢复，不重复下单；明确拒单立即反馈，不额外等待。
- 前端请求 ID 必须与币种、方向、订单类型、价格等实际订单参数绑定：参数未变时复用以恢复未知结果，参数改变时生成新 ID，不能让旧请求状态阻塞新操作。
- 用户级交易 / 归集互斥依赖 [locks.py](../server/trading/locks.py) 的共享缓存锁，默认 120 秒。绑定 / 解绑和通用交易所写装饰器统一按“API 绑定生命周期锁 -> 交易账户活动锁”取锁；开仓与归集使用专用活动锁，并在锁内复核绑定代际和 Key 指纹，不能在持有活动锁后反向申请生命周期锁。代码里有锁不等于可以用本地内存替代生产 Redis。
- 市价、限价和追单通过 [entry_guard.py](../server/trading/entry_guard.py) 复用账户活动锁、提交锁和绑定代际复核；入口只消费一次性取得的不可变账户上下文。新增开仓方式不得复制这套判断或在锁内重新选择另一个 API 绑定。
- 订单身份包含 Key 指纹、币种和交易所订单号。API 重新绑定后不能拿新的凭证管理旧 Key 下的订单；兼容历史行时仍须限制用户范围。
- 价格、数量、杠杆按交易所信息和精度校验；不得以缓存图表价格作为下单、触价保护或结算的真实依据。

## 成交与部分成交

以交易所确认的真实成交数量和成交价建仓、挂保护和发送开仓事件。创建委托成功或获得订单号不等于已成交。

限价部分成交需要接管已成交部分的保护；追单先确认旧委托撤销状态。撤单结果未知时不得直接再下完整市价单，否则可能重复敞口。减少 / 关闭仓位要区分本次实际数量与历史累计数量，保护单与策略更新都应围绕真实剩余仓位。

成交数量已确认但均价缺失时，保留已知成交数量及待确认身份，不能将其降为“撤销、零成交”，也不能据此追单或改判为手动仓。订单查询 / 撤单适配不把缺失数量填成零，不用委托价格充当成交均价；较旧回包不能用更少数量的均价拼接更大仓位。限价入口观察到未确认的正数量即保存证据，限频仍立即中断，单笔同步与追单在账户锁内刷新已知数量和状态。

## 止损保护

- 替换已有止损或止盈条件单时，先创建新单并在短窗口内按 `0.15 / 0.35 / 0.75 / 1.25` 秒退避确认可见，再撤旧单；条件单详情短暂不可见时须结合活动挂单交叉确认，持续不可见则回滚新单并保留旧单，不能制造无保护窗口。
- 初始止损挂单失败不立即强制平仓，先保留已成交仓位并进入保护重试 / 对账；若价格已触及保护触发条件，则走紧急退出路径。
- scheduler 每 10 秒运行保护对账，实际调度有抖动和网络延迟，不能承诺缺单后恰好 10 秒内修复。
- 快速尝试之后按 10、10、30、60、120、300、600 秒逐步重试；触价检查不受补单退避时间阻塞。
- 不因交易所暂时查询失败把订单误判为平仓；止损 / 止盈状态、真实持仓与结算需按各自对账路径处理。
- 已挂策略保护是订单运行状态，不能靠编辑用户默认策略改写已有订单的策略快照。

历史提出的数据库触发器 / 离线管理员口令、止损丢失立即企微 / TG 告警尚未有完整实现及验收依据。有保护状态字段或重试逻辑，不等于这些方案已经上线。

## 外部手动仓位强制保护

整合版保留 [external_positions.py](../server/trading/external_positions.py) 的扫描与保护规则，当前未通过真实造仓验证收紧、恢复或超额退出。当前部署范围见 [变更记录](changes.md)，原实施背景从 [来源索引](sources.md) 查询。

- 普通、带单各自每 10 秒扫描有效 API 绑定，即使没有本地订单也扫描。使用新鲜仓位数据，按用户、模式、Key 指纹、绑定代际、币种及方向隔离；账户锁内复核身份。只支持 USDT 永续，账户其他合约不会阻塞该范围的扫描。
- 尚未成交的手动委托不创建仓位记录。已有 Web `Order`、待成交 `LimitOrder` 或未完成 `TradeOpenRequest` 优先由原流程管理；Web 同向外部加仓不虚构成另一笔手动仓。
- 未关联订单的开仓请求，仅在当前账户身份下有相同币种和交易所订单号的 Web 归属记录，或明确撤销 / 过期且零成交限价证据时解除扫描阻塞；已经结束的 Web 仓不阻止新的手动生命周期。未接管的部分成交、缺少终态证据及未知提交继续阻塞，不按请求年龄删除或猜测失败。
- 独立手动仓复用 `Order`，来源为 `exchange_external`，未知开仓订单号为 NULL，不发送虚构的 Web 开仓事件。活动唯一键在确认结束时释放；接管时间不等于真实开仓时间。前端显示“手动仓”，可点击“立即平仓”，保留手动止盈，禁止绑定策略或使用保本入口另起保护管理者。
- 接管时保存本模式止损额度 R；无有效正数额度则显示待配置，保留已有保护，不猜金额。后续不随默认额度变化放宽。按实时均价 E 和数量 Q 求多仓 `E-R/Q`、空仓 `E+R/Q`；Decimal 计算，多仓向上、空仓向下对齐 tick。手续费、资金费、未来滑点不包含在该额度内。
- 最终保护价只收紧；保存更严格的完整保护及其 `MARK_PRICE` / `CONTRACT_PRICE` 参考类型。取消后按原底线和参考类型重建。部分止损不视为全仓保护，更严格的部分止损和其他方向 / 止盈不批量撤销。限价止损由同价或更严格的市价保护确认后替代。
- 每轮先核对未决平仓，再比较 `max(-rawUpl, 0) > R`。超额立即提交该方向市价平仓，无论已有止损与否，不依赖条件单查询成功。等于额度不走超额分支，但已触及保护价仍退出。缺失或非有限浮盈亏视为查询失败，不能当作零。
- 新止损写前保存客户端 ID，确认回执中的身份、方向、参考价和覆盖数量后才能撤旧。活动列表暂时漏单时查精确详情，不能每轮叠加挂单。明确取消后立即补挂；外部分支按每轮周期核对，未复用 Web 的长退避或人工管理豁免。
- 平仓写前保存客户端 ID、数量上限及均价；未知结果按原 ID 恢复，不盲目重发。严格选择方向，单向只减仓，双向显式指定方向。部分成交 / 拒单后的仓位发生明显变化时，停止旧请求续单并继续风险保护。确认完整成交或连续两次成功确认目标方向空仓后才关闭本地记录。
- 已平仓的未知止损请求和撤单失败记录继续追踪清理；新生命周期不接管旧生命周期待清理的保护单，防止旧清理撤掉新仓的唯一保护。

外部历史成交及费用无法完整重建，结算标为估算，未知数值返回 `null`，页面显示 `--` / “盈亏待核对”，不进入通用真实费用或历史成交累计流程。未观测到的同向平清又重开不能保证被还原为独立生命周期；请求长期无法查证时保持未确认并禁止盲目重提，详见 [已知边界](known-issues.md#外部手动仓位保护边界)。

首次上线会管理当时已经存在的外部仓位，可能立即平掉浮亏超额仓。迁移只变更结构，不扫描或交易；发布时必须避免旧、新保护 worker 混跑。产生外部记录后不可直接回滚到不识别来源的旧保护代码。

## 平仓、结算和通知

“仓位已关闭”和“费用及盈亏结算完成”是两个状态。结算补偿需按唯一交易身份读取成交账本，区分 `settled` 真实结算与 `estimated` 估算，不能将估算数字伪装为最终金额。

平仓回执已明确为 `FILLED` 时立即完成正常路径；只有写入结果未知时才通过交易所仓位恢复，并要求连续两次确认空仓。单次查询为空或一次查询失败都不能直接清除本地订单、限价委托或保护单追踪状态。

立即平仓及两处 Web 紧急退出都传递原订单的预期方向；单向账户若旧多仓已变成新空仓，不能按当前净仓方向关闭新仓。目标方向已经不存在时仍按既有确认流程处理旧记录。

成交明细按匹配记录的字段是否完整择源，真实已实现盈亏与手续费允许为零。完整零值优先于时间窗口账单或末次成交价估算；字段缺失 / 非法时仍使用既有兜底并保留估算标记。结算与历史展示遵守同一规则，不批量重写既有结算数据。

通知盈亏比按净盈亏 / 该单止损金额表达为 R，而不是价格涨跌幅或固定名义倍数。成交费和其他结算项未确认时按现有估算标记显示；最终账本口径不能由通知 Markdown 反向推算。

平仓归因事件必须在清理保护单前持久化，避免清理动作覆盖判断证据。减仓时，剩余数量投影与减仓事件在同一数据库事务提交；事件首次持久化失败就回滚本次数量投影，等待后续对账重试。交易终态同时将 `exchange_size` 清零并复位人工加仓标记，不能把历史敞口带入下一周期。

通知事件与网络投递隔离，失败只影响对应投递状态，不回滚真实成交、不重复交易。五类字段和外发协议见 [信号与通知](signals-and-notifications.md)。开仓事件的首次入库仍是尽力而为，现有限制见 [已知事项](known-issues.md)。

带单模式在账户与能力适配器边界分流，模式进入锁、幂等、订单归属及缓存身份，复用本页定义的成交与保护语义。关闭带单入口只阻止新绑定 / 开仓 / 追单，不能停止存量持仓保护或管理；细则与官方身份局限见 [带单模式](lead-trading.md)。

## 维护检查

费用补齐、结算补偿、陈旧仓修正、异常平仓巡检及残单清理，在数据库限制批次前筛选有效绑定、模式、Key 指纹与旧无指纹记录的绑定代际；实际处理时仍复核凭证。残单队列先筛选仍有待清理标识的记录，避免停用账户或已清理记录占满批次。

涉及本主题的修改至少覆盖：重复请求、部分成交、交易所超时 / 未知结果、保护挂单失败与恢复、触价退出、跨用户 / 跨 Key / 跨币种隔离、策略快照、估算与真实结算。涉及锁或唯一约束时补隔离 MySQL / Redis 验证，不能仅凭 SQLite 单测推断生产并发安全。

历史事故说明为何严格分离发布和交易操作，但不提供可直接执行的撤保护、改豁免标记 SQL 或脚本。后续安全增强需独立设计、测试及部署记录。
