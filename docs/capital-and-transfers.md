# 资金与转账历史

资金动作与历史查询是两条不同链路，不能为了加快页面加载而触发资金动作。主要入口：[balance_cap.py](../server/trading/balance_cap.py)、[transfer_history.py](../server/accounts/transfer_history.py)、[账户视图](../server/accounts/views.py)。

规则核对日期：2026-10-01。充值及 Pay 站内转账已随 `605b8f2` 在线上运行，指定主账户 600 USDT 收款已同步并通过只读历史及重复刷新验收；其他账户 / 渠道的真实完整性不能由此推断，范围见 [变更记录](changes.md)。

本页划转与转账历史仅适用于普通合约模式。带单组合拥有独立止损额和首仓资金预检，资金调整通过币安“我的带单”页面；后端拒绝带单模式的钱包 / 归集路径，后台资金提醒和历史同步只遍历 ordinary 绑定。详见 [带单模式](lead-trading.md)。

## 半自动资金规范化

用户止损金额决定阈值：开仓下限为 1.5 倍；补充目标与合约保留上限为 5 倍。资金 / 现货小于 1 USDT 的零头按既有规则忽略，不硬编码固定美元额度。

Web 手动市价、限价和追单在新交易周期首仓前预检；持仓周期中的后续开仓不重复做首仓资金规范化，但仍保留其他风险限制。后台每 30 分钟只做检查和提醒，绝不自动补资或归集。

任何实际规范化都需要用户确认，且服务端在锁内重新确认交易所真实无持仓、无普通挂单、无条件挂单。不仅依据本地数据库；已有持仓时不得划转资金以“补保证金”。

资金规范化不自动提交开仓。一个归集仍在等待确认时，阻止重复归集；合约资金已满足条件时，不因“有待确认归集”一项单独禁止开仓。旧文档“归集未确认一律禁止首仓”已失效。

## 拟议：按钱包主动发起单笔划转

2026-10-29 用户提出用页签和独立按钮替代串联归集。下述为方案讨论与建议，尚未实施，不代表上文现行接口已改为单笔操作，也不代表此前本地按钮修复已部署。

核心是每次点击只提交一笔明确的资金动作；成功后刷新钱包，不自动提交下一笔。不再为多个钱包维护一笔“总归集”的阶段衔接。页面资格由当前真实余额及可划转额度决定，单笔历史结果独立展示。

| 页签 | 展示与动作建议 |
| --- | --- |
| 合约 | 显示余额、保留目标和超额；输入金额默认填超额，仅允许在当前可划转超额内减少；点击“划转到现货”只做这一笔 |
| 现货 | 显示可用余额；“转入合约”默认填当前缺口与现货可用额中的较小值，无缺口则置灰；“转出至预置收款账户”显示网络与地址尾号，独立提交 |

保留目标建议继续沿用 `5 × 止损额`，1000 U 只是止损额 200 U 的示例。设目标为 T、合约余额为 F、现货可用额为 S，金额均用 Decimal 并按实际精度处理：

- 合约可转现货：`max(F - T, 0)`，同时受真实可划转额度限制。
- 现货可补合约：`min(max(T - F, 0), S)`。
- 现货可向外转出建议值：`max(S - max(T - F, 0), 0)`；先保留补足合约所需金额，外部转出仍需校验所选网络的费用、最低额及可用性。

例如 F=800、S=500、T=1000，页面可同时显示补合约 200、向外转出 300；不需要保存“补资完成后再进入转出”的总流程。每次提交在账户锁内重读真实状态并校验用户确认的金额；额度不足时刷新显示，不擅自改金额执行。涉及资金动作仍沿用既有无真实持仓 / 无挂单校验，不能把拆按钮理解为放宽保证金边界。

本提案中的“预置收款账户”指外部收款目标，与币安自身“资金钱包”不同。主账户显示预置网络 / 地址尾号；子账户仍仅走所属主账户，不改成外部地址提现。现有币安资金钱包不由这两个页签暗中归集，是否增加独立资金钱包页签另行明确。

### 最小执行记录与安全边界

每笔仅独立保留成功、明确失败、待确认三类结果，以及用户 / 模式 / Key 身份、原请求编号、方向、金额、尝试时间、目标快照和交易所流水号。请求重试复用原编号；刷新、切页签和查询结果不提交新划转。结果未知时防止相关重复转出，但不再恢复一条跨钱包的后续执行链。

余额变化用于重新计算按钮额度，不能单独证明上一笔成功；余额也可能因其他交易、扣费或用户直接操作而变化。例如当前合约已到目标时可将超额显示为零、禁用继续转出，原请求仍按回执独立核对。提现申请返回 ID 表示申请受理，完成状态另查本笔提现历史，参见 [Binance 提现及提现历史](https://developers.binance.com/en/docs/catalog/core-trading-wallet/api/rest-api/capital)。

收款目标建议改为服务端受控白名单，普通页面和资金请求不能新增或修改地址 / 网络。当前 [CapitalCollectAccountView](../server/accounts/views.py) 仍允许登录用户修改地址与网络，不能仅把前端输入框隐藏就声称已经锁定；实施时需要同时收紧该写入口。提交只引用服务端目标；展示目标与实际执行目标必须一致，目标变化需重新确认。固定目标之外仍需用户 / 绑定隔离、重复请求防护和可划转额度校验。

现有合约与现货双向划转、子转主和地址提现适配器可复用；目前 HTTP 层仍是归集预检 / 规范化接口，独立单笔接口与记录尚未实现。切换时保留旧流水，只核对其已提交请求；未提交的后续步骤不由新页面自动续跑，旧未知结果不能靠清记录绕过。迁移及同账户并发的具体实现与验证需在实施时落实。

## 持久化阶段与未知结果

```text
用户确认 + 交易所空仓 / 无挂单检查
    --> 资金 -> 合约
    --> 现货 -> 合约
    --> 合约 -> 现货
    --> 资金 -> 现货
    --> 现货 -> 所属主账户或预设目标
    --> 流水对账确认
```

各阶段按实际余额和目标决定是否执行，不是每次固定跑五笔。`CapitalSweep` 持久化绑定 Key 指纹、阶段金额、尝试时间和交易所流水号；数据库仍限制每个 Web 用户只有一个活动槽位。相同 Key 重绑可复用同一指纹下的流水；不同 Key 留下的活动流水会阻断新归集并要求人工核对，不能由当前 Key 接管，但它不阻断开仓资格判断。

每步先记尝试再调用交易所；请求超时可能已经转出，恢复时查精确历史，不盲目再次划转。内部划转恢复只接受提交前 1 秒至提交后 5 分钟内，且币种、金额、方向 / 类型、成功状态和所需对手方全部匹配的记录；`status` 或要求的 `type` 缺失时不得用成功默认值补齐，子转主记录还必须明确返回 `counterParty=master`。窗口外或字段不完整都保持待确认，不猜测成功也不自动重提。外部直接操作交易所无法与本地锁形成原子事务，步骤间状态变化需中止或等待对账。

### 手动面板与阶段衔接

- 打开归集面板调用 `refresh_capital_precheck`：使用与归集 / 开仓相同的账户活动锁，先核对已提交步骤的精确回执，再读取当前钱包并展示计划。此路径可以更新本地流水终态并触发原有完成邮件，但不会提交任何新的交易所划转。开仓 / 追单预检和后台提醒仍使用不改流水的 `capital_precheck`。
- 用户确认后，同一请求内顺序执行可完成的步骤。返回内部流水号才推进；空回执和未知结果保留当前阶段。主账户转出申请受理后立即查一次提现历史，不把“已受理”当成“已到账”。后续已提交步骤只查回执，不再重复读取全部持仓、挂单、余额或探测账户类型；确认回执后若还有未提交步骤，则重新核实真实活动和钱包。
- 已确认内部划转后，末步转出前重新读取现货可用额。交易所钱包尚未更新时保留同一笔计划等待，避免尚无可用余额就发送转出请求。短暂可见性宽限为 60 秒，按已确认步骤的原提交时间计算，轮询不会延长宽限。未提交的剩余计划与实时余额仍不一致时重新展示计划，不自动执行新金额；已经提交且结果未知的步骤不受此取消规则影响。
- 前端在用户确认后自动跟进同一 `collection_id`：间隔 2、5、10、20、30、30、30 秒，最多 7 次后续请求，启动后不再发起超过 3 分钟的新查询。单次只运行一个请求；成功、需重算、关闭、隐藏、离线、退出 / 换绑定 / 切模式时停止跟进。中断不会撤销已提交请求；再次打开只核对，继续执行仍须点击确认。首次确认超时而未取得编号时不自动重放。
- `POST /v1/trade/capital/normalize` 新增可选 `collection_id` 和 `expected_plan`。新前端继续请求固定流水编号；旧编号已完成时只返回它的结果，不能接管较新的流水。首次确认携带预检 `plan_token`，锁内重新规划若发现金额、阈值或目标配置变化，返回 `plan_changed` 让用户重看。金额始终来自服务端规划，标记仅作变化检测；旧调用方参数仍兼容。
- 响应中的 `completed_steps` 驱动逐步对勾。提示面板保留本笔全部路径与金额，包括 `合约 -> 现货` 和 `现货 -> 主账户`；旧笔尚未确认时明确标示旧流水与当前新增合约超额。`GET /v1/account/info` 返回只读 `pending_capital_collection`，用于显示独立的“核对上次归集”入口，不再强制点亮“归集余额”。

2026-10-29 按用户要求简化账户页入口（本地实现，尚未发布）：

- “归集余额”只用于转出超额：合约余额加可划转资金 / 现货余额，超过 `5 × 止损额` 且超额至少 0.01 U 才启用；单个资金 / 现货钱包不足 1 U 的残差仍忽略。止损额为 200 U 时，900 U、1000 U 置灰，1000.01 U 可启用。前端阈值与加减比较使用现有 Decimal 库，避免浮点误禁用。
- 关闭面板即丢弃其显示状态，重新打开向服务端读取；按钮资格只取当前余额和阈值，不叠加旧弹窗状态。纯补入合约、没有转出金额的计划在该面板显示“无需归集”；需要纯补资时先在币安侧补入合约，前后端开仓提示同步指向币安。后端原有资金规范化接口和开仓预检规则保持现行口径。
- 继续核对旧笔并确认完成后，再调用一次仅核对、不提交新划转的预检。有新的超额计划就直接展示，仍需用户再次确认；没有新计划则保留旧笔完成结果。新计划读取失败保留完成结果并提示重新检查，不能重发旧笔。

此处简化的是页面资格与完成后的衔接。账户锁、真实持仓 / 挂单复核、固定流水编号和未知结果只查回执仍然必要：它们避免重复转账和移动持仓保证金，不用清空旧记录或按超时猜测完成来替代。

不新增后台自动转账任务、数据库迁移或新的交易所端点。严格回执匹配、每用户单一活动槽位、API 绑定隔离和 1.5 / 5 倍规则保持原口径。交易所持续不提供有效回执时仍只能保留待确认；不能用本地时间到期或余额下降证明转账完成。

## 主 / 子账户和完整到账

- 主 / 子账户身份通过现有两个探测接口综合确认；不能只看到 Binance `-8012` 就认定为主账户。身份未知时不进行转账。
- 子账户向所属主账户使用 `subToMaster`，子账户 Key 不应开提币；不能传任意邮箱、UID 或外部收款地址替换这条路径。
- 绑定主账户并明确启用向另一主账户归集时，使用预配置 Spot 充值地址及网络，支持 BSC / TRX / ETH；这是需要提币权限、IP 限制和审计的另一条路径，不是所有账户默认都开提币。
- 主账户归集使用文档化提现接口，`transactionFeeFlag` 必须发送小写字符串 `"true"`，将符合条件的内部转账手续费退给收款账户，避免“转 100 到账 99.99、0.01 退回发起账户”的旧行为。
- 这不保证任意链上提现免手续费。申请成功不是到账成功；恢复时必须精确匹配本次 `withdrawOrderId`、币种、金额，并在交易所返回相应字段时同时核对冻结的地址和网络。状态 6 / `COMPLETED` / `SUCCESS` 才是完成；已完成的站内或链上转出都必须记为终态，不能因链路类型不同而再次提交。当前金额匹配容差 0.1 只用于兼容交易所提现记录口径，应与手续费返还语义区分，不能把容差当到账金额承诺。

提现 / 内部划转适配见 [common/binance.py](../server/common/binance.py)，业务对账见 [balance_cap.py](../server/trading/balance_cap.py)。修改端点或 Binance 字段时重新核对官方文档与测试，不能仅凭本说明推断未来接口规则。

## 转账历史：打开读库，刷新才同步

| 操作 | 当前行为 |
| --- | --- |
| 首次进入历史页面 | 前端可先显示用户范围内存快照，GET 读取服务器数据库，不等待 Binance 查询 |
| `GET /v1/account/transfer-history` | 只读数据库，默认每页 20 条；总计为当前完整范围统计，不仅当前页 |
| 右上角刷新 / `POST /v1/account/transfer-history/sync` | 立即请求交易所增量同步并入库，可能比普通打开耗时更长 |
| 每日 00:10 Asia/Shanghai | scheduler 自动增量同步入库 |
| 第一次同步 | 自 2026-08-28 北京时间开始补历史 |
| 入金来源升级后的第一次同步 | 旧同步状态的 `source_version<2`，从同一起始日补查充值、Pay 与账户对应的转出来源，全部成功入库后标记为版本 2 |
| 后续同步 | 从上次成功游标回看 3 天，覆盖迟到流水并幂等更新 |
| 同步失败 | 不前移成功游标，保留旧历史和统计；前端不应因刷新失败清空已展示内容 |

当前展示已完成的 USDT 转账，不是任意币种、任意日期的完整财务账簿。净转出 = 累计转出 - 累计转入，不能命名为交易利润。不同账户类型查询对应的转账 / 充提历史，遵循交易所时间窗口和分页限制。

入金来源包括主账户和子账户的充值历史：链上充值显示“外部账户”，币安站内地址转账显示“币安账户”；按交易所 `walletType` 展示实际目的钱包（0 现货、1 资金，缺失或未知则显示“账户”）。只统计充值 `status=1`，待确认、拒绝或 `status=6`（已入账但暂不可提现）不纳入当前“已完成”统计。子账户另外保留所属主账户 / 其他币安账户的划转记录；主账户保留现货提现、子账户保留现货转出的原有口径。

UID / 邮箱 / 手机号转账可能出现在 `/sapi/v1/pay/transactions`，不在充值历史中。普通主 / 子账户均查询 Pay：USDT 金额为正记转入，为负记转出并保存绝对金额；按该接口的钱包枚举（1 资金、2 现货）显示路径。Pay 的 `000000` 只有 HTTP 2xx 且 `success=true` 才算成功；数据列表异常直接使同步失败。流水 ID 沿用交易所 `transactionId` 的稳定哈希，不保存对手的 UID、邮箱、手机号、姓名或完整响应。缺少流水 ID、无效金额 / 时间不生成猜测记录。

此前主账户会过滤资金钱包充值，子账户完全不查充值历史，导致外部入金漏显。修复共用充值查询，并用来源版本保证升级前超过 3 天的漏项也能补查。同一币安账户的现货、资金、合约钱包之间移动不计作新的外部入金。每个来源按交易所流水标识幂等更新，不用相近时间或金额猜测跨来源重复；账户划转与地址充值没有已验证的通用关联 ID，不擅自合并。充值响应格式异常或任一来源读取失败时，整次同步失败，旧记录、成功游标与来源版本不变。

新增 `accounts.0003` 仅增加带数据库默认值 0 的同步来源版本字段，不读取交易所、不搬动资金、不在迁移中补历史。旧代码可继续读写迁移后的表，已补齐记录不会因代码回滚自动删除；部署后由用户点击刷新或每日任务执行一次补查。补查仍受交易所分页、权限及请求预算约束，失败后下次从同一起点重试，不把部分数据当成完整结果。接口语义参考 [Binance 充值历史](https://developers.binance.com/en/docs/catalog/core-trading-wallet/api/rest-api/capital) 与 [子账户资产划转历史](https://developers.binance.com/en/docs/catalog/vip-and-institutional-sub-account/api/rest-api/asset-management)。

Pay 补齐只将来源版本从 1 提升到 2，无新增迁移。查询每页最多 100 条、时间窗口小于 90 天；满页拆成不重叠的时间段，单毫秒仍满页则明确失败，避免静默丢记录。每次 Pay 查询消耗 UID 权重 3000，使用该端点独立的 180000 / 分钟上限及现有后台预留比例，按 Key 指纹代理账户隔离预算，并观察 Pay 的 UID 权重响应头；现有其他 SAPI 预算保持原口径。没有已验证的跨 Key UID 关联，同一币安账户使用另一 Key / 官方页面的用量需依靠响应头与交易所限频回执校正。大批量补查仍可能触及预算并失败，不承诺无限历史可一次拉全。接口和限额参考 [Binance Pay 历史](https://developers.binance.com/en/docs/catalog/investment-and-services-pay/api/rest-api/~) 与 [SAPI 限额说明](https://developers.binance.com/en/docs/products/advanced-earn/general-info)。

若回退到不识别来源版本的旧同步程序并运行超过 3 天，再次升级时需针对受影响绑定重新触发完整补查；回退到来源版本 1 的程序后再次升级会因版本不足自动回补。子账户自身 Key 的充值 / Pay 查询权限与真实历史完整性尚未实盘验收；权限拒绝按同步失败处理，不能静默视为零入金。

同步锁按用户 + Key 指纹建立，有效期 120 秒。同步开始时冻结绑定代际，交易所响应返回后再次复核；重绑期间完成的旧请求不得写入当前 Key 的历史或推进当前游标。主账户窗口按小于 90 天拆分；子账户结果达到上限时拆时间段，无法保证完整性时明确失败，不能静默截断后给错误总计。

## 为什么还与 API Key 绑定

当前历史记录和游标使用 `user + api_key_fingerprint`，相同 Key 重绑可复用，换一把 Key 则进入另一个历史范围。数据库里的 `binance_uid` 历史字段不代表当前已经有可靠的交易所账户身份关联。

这不是断言 Binance 账户永远无法绑定，而是当前链路没有已验证、可跨 Key 稳定使用的账户身份契约。将来要按账户归档，先确认可用身份来源、账户类型、权限、冲突迁移与隔离测试，不能用昵称、邮箱或前端 token 猜测合并。

前端缓存见 [data.ts](../tools/src/pages/transfer-history/data.ts)，按用户 ID 或邮箱隔离，不按短期 access token；只保留内存快照，不把财务记录放 localStorage。异步代际保护防止旧账号请求覆盖新账号页面，退出 / 绑定切换流程需要验证失效。

## 排障与验收

打开仍慢时分开测页面代码加载、API 网络时间、JWT 刷新和服务端数据库时间。GET 只读库仍包含网络往返，不能承诺全地域固定毫秒数；首次打开 1-2 秒本身不能证明仍在查询 Binance。

检查请求是 GET 还是显式 POST 同步、是否发生401刷新、是否命中用户内存快照、后端查询是否带正确指纹和索引。排障不自动执行 `sync_transfer_history` 管理命令：该命令会查询交易所并写库，不是纯诊断。

账户余额读取失败时，前端保留该 Web 用户上一次成功值；从未成功读取则显示 `--`，不能把错误占位符转换成真实 `0`。这只是显示降级，归集预检和执行仍必须由服务端重新读取交易所真实持仓、挂单和钱包余额。

历史仓位的旧结算补齐受私有接口预算约束：超过 89 天的旧记录不再请求 Binance 历史，单次页面请求最多修复 2 笔，后台每轮默认最多处理 5 笔；任一路径命中 Binance 限频后立即停止本轮。余额接口一次合约请求同时取得可用余额和总权益，不再为已移除的“今日盈亏”额外查询账单。
