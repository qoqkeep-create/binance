# 带单模式第一阶段实施计划

**Goal:** 同一 Web 用户分别绑定普通合约与带单组合 API，复用开仓、持仓保护和历史界面，严格隔离交易归属。

**Architecture:** 使用同一绑定模型和凭证服务，以 `(user, trading_mode)` 唯一；模式通过请求和订单显式传递，不保存为服务器全局当前模式。共享合约执行及保护服务，带单适配器负责账户能力、USDT 白名单与资金边界。普通模式身份和默认行为保持兼容。

**Tech Stack:** Django / MySQL、Redis、React / TypeScript、Binance Futures 与 Copy Trading API。

## 已核对的官方边界

- [官方 API](https://developers.binance.com/en/docs/catalog/advanced-trading-copy-trading/api/rest-api/future-copy-trading)：带单身份与币种白名单两个只读接口；实际交易复用 Futures 接口。
- [创建带单组合 API](https://www.binance.com/en/support/faq/detail/2bec848b904b422197ce121d0925f20b)：独立组合 Key，只支持 USDT Futures，不支持 Multi-Assets Mode；关闭组合会删除 Key；订单限制 20 次 / 10 秒，资金通过币安带单页面划转。
- 身份接口声明的是“用户是否带单员”，不能将其夸大为任意 Key 都已证明属于指定组合。绑定界面必须明确要求从该组合页面创建 Key。

## 设计取舍

扩展现有绑定模型，避免新增一套加密、凭证健康与生命周期服务。调用面已确认没有业务代码依赖 `user.api_binding` 的反向一对一属性。显式模式过滤覆盖全部绑定查询、订单归属、后台调度与幂等记录；新增数据默认为 ordinary，保留旧行与普通模式锁键。

首期带单界面提供开仓、持仓、历史、API 管理及独立止损额度。策略模板复用，订单策略快照继续独立。资金归集和转账历史仅普通模式可用；带单资金门槛仍检查该组合合约权益，需调整时提示去币安处理。

## 实施与验证

1. 绑定及账户上下文：模式定义、双绑定唯一约束、独立止损额度、凭证与代际查询；补跨模式 / 跨 Key 测试。
2. 带单适配器：严格解析身份 / 白名单、USDT 限制、资金接口禁用、共享 IP 预算及带单订单短窗口预算；契约与失败测试。
3. 交易全链路：请求模式、开仓 / 限价 / 追单、幂等与订单落库、列表 / 历史 / 平仓 / 止盈止损、后台按订单模式解析凭证。切换页面不能停止另一模式的保护。
4. 前端：模式切换、独立绑定及数据缓存、不同配色、旧请求不覆盖新模式、隐藏首期未适配功能。
5. 回归：SQLite 全量、前端测试 / 构建、MySQL / Redis 隔离并发测试；不使用真实交易或划转验收。
6. 发布：先部署兼容模式字段但未开放带单的基线，验证后再开放入口。存在带单绑定后，不可直接回滚到不识别模式的旧代码；代码回滚不回滚数据库。
