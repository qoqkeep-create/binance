# 外部手动仓位强制止损实施规划

状态：2026-09-30 已完成实现与模拟交易测试，按用户后续明确要求将 `85d47b0` 推送至 `main` 并部署，普通 / 带单扫描任务已启用。上线时暂无外部仓记录，未通过真实造仓验收各保护及退出边界；带单鉴权配置阻塞见 [已知事项](../known-issues.md)。本文件保留规划基线和实施取舍；维护规则以 [交易安全](../trading-safety.md#外部手动仓位强制保护) 为准，实际验证范围见 [变更记录](../changes.md)。

实施结果：复用 Order，新增 0027 结构迁移；普通 / 带单各自每 10 秒扫描；面板标“手动仓”，支持立即平仓。请求结果未知时只核对原 ID，不通过重启或多次查无结果强行重下；无有效额度、无法查证的请求和未观测到的同向重开边界见 [已知事项](../known-issues.md#外部手动仓位保护边界)。保护底线同时保存触发参考类型，避免重建 MARK_PRICE 止损时变成成交价触发。外部分支按周期重试，未引入 Web 长退避；新旧生命周期的遗留保护分开处理。

目标：扫描已绑定账户中的非 Web 手动仓位，补齐或收紧止损，持续恢复被取消的保护；每轮发现浮亏超过止损金额时立即提交该方向的市价平仓。

架构：复用 `Order`、现有 scheduler、账户锁、Binance 客户端及保护单创建/确认流程。增加一个外部仓位识别服务和少量来源/幂等字段，不增加服务、消息队列、交易历史回放系统或独立仓位表。

技术栈：现有 Django、Decimal、MySQL、Redis、APScheduler；前端沿用现有持仓页。

## 1. 已明确的产品规则

| 扫描结果 | 动作 |
| --- | --- |
| 外部实际持仓，浮亏超过该仓位止损金额 | 本轮立即提交目标方向剩余仓位的市价平仓；无论是否已有止损 |
| 浮亏未超额，未挂有效止损 | 按金额计算目标价并创建全仓止损 |
| 浮亏未超额，原止损预计亏损超过金额 | 先建符合要求的新止损、确认有效，再撤掉被替代的旧单 |
| 原止损合规或更严格 | 保留并记录有效保护价，之后不能自动放宽 |
| 用户取消止损 | 发现取消后按记住的保护价补回；若此时浮亏已超额，直接走平仓 |
| 用户把止损改宽 | 收紧回保存的保护底线；更严格且有效的修改可更新底线 |
| 用户关闭策略、出现人工管理标记、服务重启 | 外部仓位继续强制保护，不能因此豁免 |
| 无真实持仓，只有未成交的手动开仓委托 | 暂无可保护数量；成交后保护实际数量，部分成交同样处理 |

用户补充明确替换初版的“超额后在现价附近挂止损”建议，不能保留那条执行分支。本文中的“立即”指扫描取得新鲜、有效仓位数据后在当前轮次优先提交，不代表轮询能够零延迟发现或保证成交损失恰好等于额度。

## 2. 识别、入库与范围

建议入库，以便重启恢复、记录保护价和未知请求。账户按用户、模式、Key 指纹和绑定代际校验；仓位按币种及方向匹配，禁止仅按币种匹配双向仓位。

扫描有效 API 绑定，包括没有任何本地 `Order` 的账户。只处理本系统支持的 USDT 合约；普通模式和带单模式分批并读取各自配置，不混用额度或凭证。当前 Key 不能代替旧 Key 操作旧记录；不同 Key 是否指向同一实际账户仍遵守现有身份限制。

在账户活动锁内重新核对本地活动 `Order`、`LimitOrder`、`TradeOpenRequest`。有 Web 未完成成交接管或结果未知记录时，先沿用其恢复路径，不能因为本地暂时缺行就认定是外部开仓。无冲突且真实非零持仓才能接管。

- 独立外部仓位：创建 `position_origin=exchange_external` 的 `Order`，初始不绑定策略，不伪发 Web 开仓成功事件。
- Web 仓位上的外部加仓：保持一个 Web 管理者和原风险快照，按真实总数量处理既有保护；交易所已合并的同向数量不能虚构成两份独立仓位。新增强制接管分支不重复管理它，也不借本需求修改原 Web 人工接管标记。
- 已入库外部仓位的加减仓：更新实际均价和剩余数量，重新核算额度，只收紧保护价；不会因减仓自动放宽止损。
- 仓位确认结束后关闭记录、释放活动唯一槽位；再次开仓属于新生命周期。发现方向反转时严格隔离，不能让旧平仓请求作用于新方向。

内部追踪直接使用 `Order.id`。未知真实开仓订单号用 `NULL`，不能将自造字符串写进 `binance_order_id`。增加可空、唯一的外部活动槽位键（账户身份 + 币种 + 方向的稳定摘要），关闭时在事务内清空；MySQL 多条历史外部记录的空开仓号不能发生唯一约束冲突。

## 3. 金额和保护价

首次接管读取当前模式的有效预设金额 R，保存为这次仓位的风险快照。后续维持该额度和保护底线；用户修改默认额度不会使已接管仓位的保护放宽。配置无有效正数时标记待配置错误，保留既有保护，不能猜金额或把零额度当作立即平仓指令。

令 E 为交易所持仓均价，Q 为实际数量绝对值乘合约面值，S 为止损触发价。全部使用 Decimal：

```text
多仓目标止损价 = E - R / Q
空仓目标止损价 = E + R / Q
多仓预计亏损   = max((E - S) × Q, 0)
空仓预计亏损   = max((S - E) × Q, 0)
当前浮亏       = max(-交易所 unRealizedProfit, 0)
```

保本/锁盈止损的预计亏损为零，不能对盈利取绝对值后误判为超额。浮亏优先读取新鲜仓位返回的 `upl`；缺字段或格式异常不能当作零，重新查询或记录失败。本期金额口径不包含手续费、资金费及未来滑点，不为外部历史费用增加同步链路。

价格按交易所步长向减小风险方向取整：多仓向上、空仓向下；取整后重算预计亏损，再进入现有标准化器，防止二次舍入放宽。现有通用止损标准化是多仓向下、空仓向上，不能直接用它求金额上限的初始价格。

多仓最终保护价取“金额目标、已保存底线、已确认更严格全仓保护”中的最高值；空仓取最低值。首次没有历史底线时忽略该项。止损被取消后按这个保存值恢复，不能退回更宽的初始值。若底线已触及或越过实时触发参考价，执行保护退出，不把止损移远来绕过触发。

浮亏超额判断严格使用 `当前浮亏 > R`。恰好等于 R 不命中这条比较，但若已触及止损价仍按触价规则处理。触价校验必须使用与订单 `workingType` 一致的实时价格，不能把当前适配层的 `last=markPx` 当作真实成交价。

## 4. 持续保护与紧急平仓顺序

沿用约 10 秒的后台周期；发现和管理共用外部服务入口，已有 Web 保护分支只负责 Web 记录，避免两套逻辑互相放宽/重建。复用按模式分批、账户活动锁和请求预算。查询失败与空仓分开处理。

每轮顺序固定为：

1. 锁内复核绑定身份，读取新鲜目标仓位，处理上轮尚未确认的交易写入。
2. 如已有未决平仓请求，先恢复回执和目标仓位状态，禁止再次按旧数量发单。
3. 检查浮亏是否超过 R；超额直接进入市价退出，不等待止损查询、补单退避或下一轮。
4. 未超额再检查有效止损及已保存底线；触价退出同样先于补单退避。
5. 缺失或过宽时创建/恢复保护请求，确认新单可见，再撤明确被替代的旧单；保存最新保护价和订单号。
6. 确认保护有效后清零本次补单失败计数。再次确认被取消时作为新的缺单事件立即尝试，不能沿用之前的长退避。

持仓持续期间重复检查。外部来源不调用会因“手动管理”而跳过的路径；相关 Web 取消入口不得取消其强制保护资格。进程重启从数据库底线、活动槽位和未决请求恢复。

识别止损需验证活动状态、币种、平仓方向、原始 `positionSide`、触发价、覆盖数量及平仓语义。解析层补充 `reduceOnly`、`closePosition`、`workingType`、`priceProtect`，才能正确识别手动全平条件单；不能把任意反向开仓 STOP 当作保护。

新增保护采用现有 `STOP_MARKET` 方式。已有合规限价止损保留其更严格价格，但限价条件单可能不成交，需要补市价兜底再安全替换，不能宣布其具有市价退出保证。部分保护不代表全仓保护，不新增复杂的分段金额分摊器；补全仓保护时保留更严格的部分保护，不批量取消止盈或其他方向订单。

平仓路径需做以下最小补强：

- 提交前持久化本次客户端请求 ID、目标方向和数量；同一次未知结果始终按相同 ID 查证。复用现有 `emergency_close` 保护状态和关闭确认能力，避免新增独立流水表。
- 平仓适配器严格选择指定方向；规划时发现的 `close_position()` 方向缺失回退已移除，找不到目标方向不能取第一条仓位。
- 单向仓位只减仓；双向仓位明确指定方向与合法平仓 side。交易所规则不允许双向模式发送 `reduceOnly`，不能用不合法参数冒充安全保证。
- 明确全部成交后持久化关闭；未知结果先按请求 ID 查询，再连续确认目标方向空仓。部分成交在确认前次请求终态后，仅对真实剩余数量发起新尝试。
- 平仓失败保留旧保护并记录错误；每轮继续优先对账/退出，通知故障不阻塞它。确认已平仓并持久化归因后再清理属于本次仓位的保护单。
- 若同方向在两次扫描间平清又重开，不能凭当前数量推断仍是旧仓位；未决请求优先用真实回执/成交锚点恢复。证据不足时禁止用旧请求再次市价平仓；当前新仓仍按现有快照补保护。首期不承诺精确还原未观测到的全部外部交易历史。

稳定客户端 ID 只用于恢复身份，不能把“重复使用 ID”当成交易所永久去重保证。创建止损未知时亦先查详情和活动订单，禁止每轮生成新 ID 叠加订单；明确取消后的补单使用新尝试身份。

## 5. 数据与现有生命周期兼容

在 `Order` 上已增加来源字段、外部活动唯一键以及两个 JSON 保护/平仓请求记录；复用已有保护状态、时间、重试计数和价格字段。0027 迁移只调整结构，不扫描账户或下单。

外部记录的 `created_at` 是发现时间，不冒充真实开仓时间。费用同步排除缺失真实开仓号的外部记录；历史盈亏不完整时维持估算/未确认标记，不进入已完整结算口径。

现有生命周期在找不到开仓成交时以 `order.size` 起算，再读取发现前几秒的成交，会对外部初次建仓重复累计。外部分支必须使用发现时的快照及明确的成交边界；只对快照后的变化记增量。无法精确归属的账本保持估算，不能“复用”成错误平仓认定。

前端返回 `position_origin`，按用户最新要求显示“手动仓”与真实保护/退出状态，提供立即平仓。接管时间与未知历史金额明确区分。新增来源不会自动带入默认止盈策略。持仓页补齐按币种 + 方向匹配，避免双向仓位覆盖。

以下实施拆分已完成，先以行为测试及独立审查暴露问题再修复。表格保留原规划的验收目标，最终测试范围与局限以变更记录及已知事项为准。

| 步骤 | 文件 | 验收重点 |

| 1. 风险判定纯逻辑 | 新增 `server/trading/external_positions.py`、`server/trading/test_external_positions.py`；复用 `server/positions/projection.py` | 多空金额、锁盈止损、Decimal 舍入、严格超额比较、只收紧 |
| 2. 数据与来源 | `server/positions/models.py` 及下一号 migration；`server/positions/lifecycle.py`、`server/positions/views.py` | 活动唯一槽位、空开仓号、关闭后再开、不伪造费用/开仓时间 |

| 4. 持续保护 | `server/trading/services.py`、`server/common/binance.py`、`server/common/tests.py`、`server/positions/cleanup.py` | 取消后补回、改宽收紧、更严格价保存、先建后撤、数量和 closePosition 识别 |

新增必测情景：

- 额度 100 U：浮亏 99 U 且缺单时补单，浮亏 101 U 时平仓；浮亏恰好 100 U 单独测比较和触价分支。
- 已有合规止损且浮亏 101 U，仍在当前轮提交平仓；止损查询失败也不能阻塞已有新鲜仓位数据上的超额退出。
- 取消、再次取消、收紧后取消、服务重启、策略取消、人工管理标记均不能永久关闭外部保护。
- 有活动保护但更严格价格尚未保存、部分止损、全平条件单、反向开仓条件单分别测试。
- 条件单或平仓 POST 成功但响应超时、提交后数据库故障、进程崩溃恢复，不重复发单或误撤原单。
- 手动改数量/翻方向、同币种多空并存、平仓与止损同时成交、快速平清重开，均不反向开仓或操作另一方向。
- 平仓未确认不能清理保护/把记录改为关闭；补单失败有持久化错误；新一轮超额不受历史退避阻塞。
- 新接管之前的历史成交不重复记入；未知费用不标为真实结算；未成交手动委托不制造本地已成交记录。

本地针对性命令（实现后，在 `server/`，使用可用的项目 Python 环境并模拟全部交易所写操作）：

DB_ENGINE=sqlite USE_REDIS_CACHE=False RUN_SCHEDULER_IN_WEB=false .venv/bin/python manage.py check

预期：对应行为用例全部通过、无迁移漂移、Django 系统检查通过。MySQL/Redis 唯一性和并发使用 [开发文档](../development.md) 的隔离 Compose；普通测试不执行生产开平仓、撤保护单。前端改动运行相关测试、typecheck 与 build。

## 7. 上线与回退边界

本轮已实施并于 2026-09-30 随 `85d47b0` 上线。用户已经明确功能应自动补回保护并在超额时平仓，随后明确要求推送并部署；首次启用影响已告知，线上扫描由正式 scheduler 执行，不另外手工运行扫描或造仓验收。

实施完成后先核验账户范围、迁移兼容和测试证据，再按当时发布指令启用。需要明确告知首次启用会接管当时已存在的外部仓位，并可能立即关闭超额仓位。普通/带单分批扫描复用现有调度，不把交易扫描放进迁移、启动检查或健康检查。

旧程序不识别外部来源和生命周期，产生外部记录后不可直接回滚到旧保护 worker。发布/回退需暂停旧 worker 的管理、保留交易所现有保护并使用识别新字段的兼容版本；不能靠撤保护或删记录实现回退。代码回滚不会恢复已经执行的交易。

上线状态已同步到架构及带单关联说明，实际部署 / 验收日期和范围见 [变更记录](../changes.md)。长期维护规则已合入交易安全主文档；本规划保留实施基线，不代替现行规范。

## 8. 核对依据

实施前核对：原保护入口仅扫描活动 `Order`；人工管理豁免在 `_group_protection_orders()`；原紧急退出以保护不完整为前提；交易所 `unRealizedProfit` 已映射为 `upl`。这些差距已由独立外部分支处理，严格比较使用新增保留的 `rawUpl`，没有把 Web 分支改成外部强制管理规则。

2026-09-30 核对 [Binance USDⓈ-M 交易接口官方文档](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/trade)：仓位接口提供方向、数量、均价、标记价与未实现盈亏；普通及条件订单有客户端身份；单向/双向的 `positionSide` 和 `reduceOnly` 约束不同。保护单的类型和参数校验、未知结果恢复须按这些契约测试，不将客户端标识当作永久幂等保证。
